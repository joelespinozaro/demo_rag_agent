Arquitectura objetivo

El navegador nunca llama directamente al Agent API — cada salto tiene una responsabilidad y una identidad clara.

Frontend → Gateway

ID token del usuario emitido por Identity Platform, en Authorization: Bearer ….

Gateway → Agent API

ID token de Google generado con la Service Account configurada en el API config.

Agent API → MCP

ID token de Google obtenido dinámicamente con la identidad de Cloud Run.

Agent API → Model Armor

Application Default Credentials de la misma Service Account.

Antes de empezar

  • Proyecto GCP con facturación habilitada.
  • gcloud autenticado (gcloud auth login) — no necesitas Docker instalado, las imágenes se construyen con Cloud Build.
  • Repositorio clonado y terminal ubicada en la raíz demo_rag_agent.
  • Credenciales para PostgreSQL, OpenAI, Groq, Qdrant y SuperheroAPI.
  • Usa Google Cloud Shell o Bash para poder ejecutar envsubst.
Costos

El laboratorio crea recursos facturables. Al terminar, elimina los servicios si no vas a seguir utilizándolos (ver Limpieza).

Todo lo que no depende de que exista ningún Cloud Run: habilitar las APIs de GCP que se van a usar, dejar lista la identidad compartida (Service Account) con sus permisos, y crear el filtro de seguridad de contenido (Model Armor). Se hace una sola vez.

1.2 Inicializar Identity Platform

bash
curl -X POST \
  -H "Authorization: Bearer $(gcloud auth print-access-token)" \
  -H "Content-Type: application/json" \
  -H "X-Goog-User-Project: ${PROJECT_ID}" \
  -d '{}' \
  "https://identitytoolkit.googleapis.com/v2/projects/${PROJECT_ID}/identityPlatform:initializeAuth"
Cada alumno, su proyecto

No es un backend compartido, así que alcanza con una sola cuenta de prueba por despliegue. El frontend solo tiene login (signInWithEmailAndPassword), no hay registro en la app — esa cuenta se crea a mano acá, dentro de tu propio proyecto.

  1. Abre Google Cloud Console → Identity Platform → Providers.
  2. Habilita Email/Password.
  3. En Users, crea una cuenta de prueba (ej. test@correo.com con una password a elección) — es la única credencial con la que vas a loguearte.
  4. Copia la API key web y pégala en el campo IDENTITY_PLATFORM_API_KEY del formulario de la Fase 0 — vas a ver cómo se completan solos los bloques de código de las fases siguientes.
Nota sobre nombres

Identity Platform usa el SDK web firebase/auth. Por eso el código conserva variables NEXT_PUBLIC_FIREBASE_*, aunque el producto de autenticación sea Identity Platform.

1.5 Template de Model Armor

El motor de content-safety: escanea prompts y respuestas antes de que lleguen al modelo o al usuario (prompt injection, contenido dañino, URLs maliciosas, datos sensibles).

Importante

Los templates solo se administran mediante un endpoint regional. El endpoint global puede responder 403 Write access denied aunque el rol IAM sea correcto.

bash
gcloud config set api_endpoint_overrides/modelarmor \
  "https://modelarmor.${REGION}.rep.googleapis.com/"

gcloud model-armor templates create "$MODEL_ARMOR_TEMPLATE_ID" \
  --project="$PROJECT_ID" \
  --location="$REGION" \
  --rai-settings-filters='[
    {"filterType": "HATE_SPEECH", "confidenceLevel": "MEDIUM_AND_ABOVE"},
    {"filterType": "HARASSMENT", "confidenceLevel": "MEDIUM_AND_ABOVE"},
    {"filterType": "SEXUALLY_EXPLICIT", "confidenceLevel": "MEDIUM_AND_ABOVE"},
    {"filterType": "DANGEROUS", "confidenceLevel": "MEDIUM_AND_ABOVE"}
  ]' \
  --basic-config-filter-enforcement=enabled \
  --pi-and-jailbreak-filter-settings-enforcement=enabled \
  --pi-and-jailbreak-filter-settings-confidence-level=HIGH \
  --malicious-uri-filter-settings-enforcement=enabled
bash · verificar
gcloud model-armor templates describe "$MODEL_ARMOR_TEMPLATE_ID" \
  --project="$PROJECT_ID" --location="$REGION"
Cómo confirmar

Debe imprimir el YAML del template con los 4 filtros RAI en MEDIUM_AND_ABOVE. Si da 403, casi seguro falta el api_endpoint_overrides del principio de este bloque (revísalo antes de sospechar de IAM).

Esto habilita: RAI (contenido dañino), prompt injection/jailbreak, URLs maliciosas, y SDP (datos sensibles) en modo básico — detecta y bloquea, pero no enmascara (no genera deidentify_result).

Opcional/avanzado — SDP con enmascarado real (Cloud DLP)

El modo básico de arriba solo detecta y bloquea. Para que el filtro sdp devuelva texto enmascarado en vez de bloquear, hay que crear un inspect template y un deidentify template en Cloud DLP (fuera del alcance de esta guía) y referenciarlos con --advanced-config-inspect-template / --advanced-config-deidentify-template en vez de --basic-config-filter-enforcement=enabled.

Cómo confirmar

El echo debe imprimir algo como MCP: https://mcp-server-service-xxxxx-uc.a.run.app/mcp. Si sale MCP: /mcp (vacío antes de la barra), el deploy del paso 2.2 falló — revisa gcloud run revisions list --service="$MCP_SERVER_SERVICE" antes de seguir. La URL usada por el cliente termina en /mcp, sin barra final — ver la nota de abajo, es al revés de lo que uno esperaría.

Pega acá lo que imprimió echo "$MCP_SERVER_URL" arriba (sin /mcp al final) — se completa solo en la Fase 3.1.
Ojo

03_mcp_server/requirements.txt fija mcp[cli]>=1.13.0,<2 a propósito — no bajes a ==1.8.0 (no propaga structuredContent, las fuentes de retrieve_documents/get_pokemon quedarían vacías) ni subas a >=2 (breaking change, FastMCP se renombró y el server ni arranca). Por qué la URL va sin barra final: el endpoint registrado es /mcp sin slash. Pedir /mcp/ devuelve un 307 cuyo Location usa http:// en vez de https:// — ese downgrade de esquema hace que httpx descarte el header Authorization al seguir la redirección (comportamiento de seguridad estándar), y la segunda petición sin token la rechaza Cloud Run con 403 — un error que parece de IAM pero es de la barra final.

3.2 Build y deploy privado

Las 5 credenciales sensibles (OpenAI, base de datos, Neon, Groq, LangSmith) no viajan como texto plano en la configuración de Cloud Run — el bucle de abajo las sube una sola vez a Secret Manager y el deploy solo referencia un puntero (agent-openai-api-key:latest), nunca el valor.

El valor no queda expuesto

gcloud run services describe muestra el nombre del secreto y su versión, nunca el contenido — a diferencia de una env var normal, legible por cualquiera con acceso de lectura al servicio.

Acceso mínimo, uno por uno

El bucle otorga secretAccessor secreto por secreto a la Service Account — no un rol amplio sobre todo Secret Manager del proyecto.

Versionado, no sobrescritura

Cada versions add crea una versión inmutable. :latest apunta a la más reciente, pero podés fijar un número y hacer rollback si una key se rota mal.

Queda auditado

Cada acceso a un secreto se registra en Cloud Audit Logs — una env var normal no deja ese rastro de quién la leyó ni cuándo.

¿Por qué no simplemente poner las keys en --set-env-vars?

Funcionaría, pero el valor quedaría en texto plano dentro de la revisión de Cloud Run — visible para cualquiera con permiso de lectura sobre el servicio (run.services.get), sin necesitar acceso a Secret Manager. Con secretos, ese mismo lector solo ve el nombre del secreto; para leer el valor necesita además secretAccessor sobre ese secreto puntual.

Recursos verificados

El contenedor carga spaCy, guardrails, LangChain y MCP durante el arranque. Con 1Gi el arranque es inestable — usa --cpu=4 --memory=4Gi, que es lo que quedó probado y estable. Si no llega a escuchar PORT=8080 revisa los logs primero (gcloud run services logs read, ver Validación) — no ocultes un cold start fallido aumentando solamente el timeout del Gateway.

04

Crear API Gateway

El Gateway valida al usuario (JWT de Identity Platform) y recién después llama al Agent API con identidad de servicio — es la única puerta de entrada autenticada al backend.

Google API Gateway es un proxy administrado: recibe la request pública, valida el JWT contra Identity Platform y, solo si es válida, la reenvía a 02_agent_api con una identidad de servicio distinta. Nada de esto vive en el código de FastAPI — es configuración declarada en openapi_gateway.yml, no lógica que tengas que mantener vos.

  1. El navegador manda Authorization: Bearer <ID token de Identity Platform>, obtenido al loguearse contra la cuenta de prueba de la Fase 1.2.
  2. El Gateway valida firma, expiración y audience del token contra el securitySchemes.identity_platform del OpenAPI — si falla, corta acá mismo con 401 y el Agent API ni se entera de que existió la request.
  3. Si el token es válido, el Gateway cambia de identidad: pide un ID token de Google para la Service Account (--backend-auth-service-account de la Fase 4.2) y lo adjunta en lugar del token del usuario.
  4. Agent API recibe la request ya autenticada como llamada de servicio a servicio, verificada por IAM de Cloud Run (--no-allow-unauthenticated) — nunca ve ni confía en el token original del usuario final.
Reduce lo que queda expuesto

02_agent_api se despliega privado (--no-allow-unauthenticated): nadie puede llamarlo directo aunque adivine la URL. La única puerta pública del backend es el Gateway.

Traduce la identidad

El usuario llega con su token; el Gateway lo cambia por un token de Google de la Service Account al reenviar. Agent API nunca maneja credenciales de usuarios finales.

El contrato vive en un YAML

Rutas, deadline y quién firma la auth están en openapi_gateway.yml — versionable (GATEWAY_CONFIG_ID) sin tocar ni redeployar el código de FastAPI.

Corta temprano lo inválido

Un JWT ausente o vencido se rechaza en el Gateway antes de despertar un cold start de Cloud Run — el backend privado no gasta cómputo en tráfico no autenticado.

¿Qué pasa si el JWT es inválido o venció?

El Gateway responde 401 Unauthorized directamente — la request nunca llega a Cloud Run. El frontend debe volver a loguear al usuario para obtener un token nuevo; no es un bug de 02_agent_api aunque el error aparezca en la consola del navegador al llamar a la URL del Gateway.

Timeout real

El OpenAPI usa deadline: 120.0. La primera llamada inicializa agente, MCP y guardrails; el límite predeterminado puede producir un 504 upstream request timeout.

4.1 Renderizar el OpenAPI

Google API Gateway sube el YAML tal cual — no soporta variables en runtime, así que hay que resolverlas antes con envsubst. GATEWAY_HOST recién se conoce después de crear el gateway (4.3); para esta primera subida usamos un placeholder, ya que servers.url es solo informativo.

Ojo con envsubst sin lista

envsubst sin argumentos sustituye cualquier patrón $VAR o ${VAR} del archivo — incluido $ref, que OpenAPI usa por todo el spec (openapi_gateway.yml solo tiene 3 variables reales: CLOUD_RUN_URL, GATEWAY_HOST e IDENTITY_PLATFORM_PROJECT_ID). Como no existe una variable de entorno ref, envsubst reemplaza cada $ref por texto vacío y rompe todos los $ref del schema — un YAML que sigue pareciendo válido pero con las referencias vacías. Por eso el comando de abajo le pasa la lista explícita de variables a sustituir, y valida el resultado antes de seguir.

bash
export GATEWAY_HOST="placeholder.gateway.dev"

cd 02_agent_api

envsubst '${CLOUD_RUN_URL} ${GATEWAY_HOST} ${IDENTITY_PLATFORM_PROJECT_ID}' \
  < openapi_gateway.yml > openapi_gateway.rendered.yml

# Verificación: falla temprano si quedó algo sin resolver o roto
if grep -qE '\$\{' openapi_gateway.rendered.yml; then
  echo "ERROR: quedaron variables \${...} sin sustituir en openapi_gateway.rendered.yml" >&2
  grep -n '\${' openapi_gateway.rendered.yml >&2
  exit 1
fi
if grep -qE '^\s*: "' openapi_gateway.rendered.yml; then
  echo "ERROR: quedó un \$ref roto en openapi_gateway.rendered.yml (revisa la lista de envsubst)" >&2
  exit 1
fi

cd ..
Cómo confirmar

Si el bloque no imprime ningún ERROR y sigue de largo, el render salió limpio. Si agregas una variable nueva a openapi_gateway.yml más adelante, agrégala también a esta lista de envsubst — si no, envsubst la deja tal cual (literal en el YAML) y el primer if de arriba lo va a detectar.

Desplegar el frontend

Recién acá se despliega lo que ve el usuario final — necesitaba el host del Gateway (recién obtenido en la Fase 4), porque las variables NEXT_PUBLIC_* se hornean dentro del bundle de JS en build-time, no se pueden cambiar después con variables de entorno de Cloud Run.

Este build necesita 4 --build-arg, y gcloud builds submit --tag (el atajo de las Fases 2.2 y 3.2) no los soporta. Por eso 01_agent-app/cloudbuild.yaml describe el mismo docker build explícitamente, y los 4 valores se inyectan vía --substitutions al invocarlo.

bash
export IMAGE_TAG=$(date +"%Y%m%d-%H%M%S")
export AGENT_APP_IMAGE="${REGION}-docker.pkg.dev/${PROJECT_ID}/${AR_REPOSITORY}/01-agent-app:${IMAGE_TAG}"

gcloud builds submit 01_agent-app \
  --project="$PROJECT_ID" \
  --config=01_agent-app/cloudbuild.yaml \
  --substitutions=_GATEWAY_HOST="$GATEWAY_HOST",_FIREBASE_API_KEY="$IDENTITY_PLATFORM_API_KEY",_FIREBASE_AUTH_DOMAIN="$IDENTITY_PLATFORM_AUTH_DOMAIN",_FIREBASE_PROJECT_ID="$IDENTITY_PLATFORM_PROJECT_ID",_IMAGE="$AGENT_APP_IMAGE"

gcloud run deploy "$AGENT_APP_SERVICE" \
  --image "$AGENT_APP_IMAGE" \
  --region "$REGION" \
  --platform managed \
  --allow-unauthenticated \
  --port 3000 \
  --cpu 2 \
  --memory 2Gi
Ojo

Las sustituciones van separadas por comas y sin espacios alrededor del = — si algún valor llegara a contener una coma (no debería, para una API key o un host), rómpelo en un cloudbuild.yaml con variables de entorno en vez de --substitutions.

bash · verificar
gcloud run services describe "$AGENT_APP_SERVICE" \
  --project="$PROJECT_ID" --region="$REGION" --format='value(status.url)'
Cómo confirmar

Abre la URL que imprime — deberías ver la pantalla de login (redirige sola a /login). Si ves texto localhost:8080 en las llamadas de red del navegador, las variables públicas faltaron durante el build: reconstruye la imagen (necesitas $GATEWAY_HOST ya definido, por eso este paso va al final).

01_agent-app sí queda público (--allow-unauthenticated) — es la app que ve el usuario final; la protección real está en que 02_agent_api solo acepta al Gateway (y 03_mcp_server solo acepta a 02_agent_api), y el Gateway solo reenvía peticiones con un JWT válido de Identity Platform.

Problemas comunes

gcloud builds submit: repository not found

Revisa que Artifact Registry exista en la misma región y con el mismo nombre de AR_REPOSITORY (Fase 1.3).

Cloud Build: PERMISSION_DENIED al subir la imagen

Falta el binding roles/artifactregistry.writer a la SA de Cloud Build (Fase 1.1) — proyectos nuevos ya no lo traen por defecto.

Permission iam.serviceAccounts.actAs

El usuario que despliega necesita roles/iam.serviceAccountUser sobre la SA (Fase 1.4).

Gateway devuelve 401

Confirma Identity Platform, issuer, audience, API key y que el frontend realmente envíe el ID token.

MCP devuelve 401/403

Lo más común: DEMO_MCP_SERVER_URL con barra final (rompe el header Authorization en el redirect, Fase 2.3). Si no es eso, confirma roles/run.invoker y la SA adjunta al Agent API.

Model Armor usa fallback

Comprueba project, región, template ID, endpoint regional y roles/modelarmor.user (Fase 1.5).

Gateway 504 + Cloud Run 503

Busca failed the readiness check. Es un cold start fallido: revisa logs, memoria (--cpu=4 --memory=4Gi) e integraciones opcionales; no es IAM del Gateway.

El frontend llama a localhost

Las variables públicas faltaron durante el build (revisa el --substitutions de la Fase 5). Reconstruye la imagen después de conocer el Gateway.

Neon/LangSmith no conectan, sin error visible

Revisa que los 5 secretos estén los 5 en --set-secrets del deploy de 02_agent_api (Fase 3.2) — falta uno y esa integración queda desconectada en silencio.

No compartas secretos

El HTML se puede enviar por WhatsApp; los archivos .env, tokens y API keys privadas no.
